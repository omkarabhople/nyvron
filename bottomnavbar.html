Building a Liquid Glass Floating Bottom Nav for iOS 26 and Android with Kotlin Multiplatform Compose

Eduardo Santos
10 min read
·
Dec 2, 2025

--

iOS now ships with a floating, glassy tab bar that feels alive over your content. In Amazing Note, that effect is wired into a Kotlin Multiplatform (KMP) app that already shares most of its UI using Compose.

On Android, you get a Material-style bottom navigation driven from the same route model. On iOS, you get a native Liquid Glass tab bar that appears only when the current screen wants it.

This article walks through how that works in the Amazing Note codebase and how you can reuse the pattern in your own KMP app:

  • How shared navigation is modeled in Kotlin and exposed to iOS
  • How LiquidRoot.swift hosts your Compose controllers in a SwiftUI TabView
  • How route callbacks from Kotlin control which tab is selected and whether the Liquid Glass tab bar is visible
  • How the same route model can drive Android bottom navigation

1. High-level architecture

Amazing Note follows a standard KMP layout:

  • shared
    Business logic, repositories, SQLDelight, Firebase, coroutines.
  • composeApp
    Shared UI written with Compose Multiplatform. This module exposes Kotlin entrypoints that build a ComposeUIViewController on iOS and a setContent {} tree on Android. Internally, it uses a simple route and back stack model (for example AppRoutes plus helpers like navigate, goBack, popToRoot).
  • app (Android)
    A classic Android launcher module that wires an Activity to the shared Composables.
  • iosApp
    An Xcode project that links against ComposeApp.framework and provides the Swift side of the UI, including the Liquid Glass tab bar.

On iOS, the interesting part lives in iosApp/LiquidRoot.swift.

2. Routes as a bridge between Kotlin and Swift

The shared UI in composeApp does not know about SwiftUI or TabView. It just knows about routes and which screens want a bottom bar.

You can see how routes are represented from the Swift side in the Tab enum inside LiquidRoot:

private enum Tab: Hashable {
    case notes, folders, settings

    init?(routeID: String) {
        switch routeID {
        case "notes":
            self = .notes
        case _ where routeID.hasPrefix("note/"):
            self = .notes
        case "folders":
            self = .folders
        case _ where routeID.hasPrefix("folder/"):
            self = .folders
        case "settings":
            self = .settings
        default:
            return nil
        }
    }
}

From this, you can infer the route IDs that Kotlin emits for iOS:

  • "notes" and "note/<id>" for the Notes tab
  • "folders" and "folder/<id>" for the Folders tab
  • "settings" for Settings

That route ID, plus a boolean for whether the bottom bar should be visible on that route, is what Kotlin sends back to Swift.

On the Kotlin side, a typical pattern looks like:

// Pseudo code approximating what your MainViewControllerKt.* functions do
fun makeNotesViewController(
    tabBarVisibility: TabBarVisibility?,           // now unused, route driven instead
    onRouteChanged: (routeId: String, bottomBarVisible: Boolean) -> Unit,
): UIViewController = ComposeUIViewController {
    NotesRoot(
        onRouteChanged = onRouteChanged
    )
}

@Composable
fun NotesRoot(
    onRouteChanged: (String, Boolean),
) {
    val backStack = rememberNotesBackStack()
    LaunchedEffect(backStack.currentRoute) {
        val routeId = backStack.currentRoute.toIosRouteId()
        val showBottomBar = backStack.currentRoute.shouldShowBottomBar()
        onRouteChanged(routeId, showBottomBar)
    }
    // Composables for the current route...
}

The important parts are:

  • Kotlin owns the navigation model and knows what the current route is.
  • Kotlin decides whether the bottom bar should be visible for that route.
  • Kotlin calls onRouteChanged(routeId, bottomBarVisible) whenever something changes.

Everything else on iOS is plumbing to interpret that signal.

3. TabBarVisibility: a single source of truth for the tab bar

At the top of LiquidRoot.swift you define an observable object:

@MainActor
final class TabBarVisibility: ObservableObject {
    @Published var isVisible: Bool = true
}

This object is created once per LiquidRoot:

@MainActor
struct LiquidRoot: View {
    @AppStorage("dark_theme") private var darkThemeEnabled: Bool = true
    @State private var selection: Tab = .notes
    @StateObject private var tabBar = TabBarVisibility()
    @State private var lastRouteHandled: String?
    @State private var lastShouldShow: Bool?
    private static var lastRouteHandledGlobal: String?
    private static var lastShouldShowGlobal: Bool?
    ...
}

TabBarVisibility is the Swift side truth about whether the iOS tab bar should be visible. It is:

  • Observed by SwiftUI to show or hide the system tab bar
  • Passed down into ComposeHost to keep the underlying UIKit controller in sync

4. LiquidRoot: a SwiftUI TabView wrapped around Compose

The body of LiquidRoot defines the iOS tab structure:

var body: some View {
    TabView(selection: $selection) {
        ComposeHost(
            tabBar: tabBar,
            onRouteChanged: { route, isBottomBarVisible in
                handleRouteChange(route, isBottomBarVisible)
            },
            controllerFactory: { tabBar, routeHandler in
                MainViewControllerKt.makeNotesViewController(
                    tabBarVisibility: nil, // avoid double-driving visibility; route decides instead
                    onRouteChanged: routeHandler
                )
            }
        )
        .id(themeHostIdentifier)
        .ignoresSafeArea(edges: .vertical)
        .tabItem { Label("Notes", systemImage: "note.text") }
        .tag(Tab.notes)
      
        ComposeHost(
            tabBar: tabBar,
            onRouteChanged: { route, isBottomBarVisible in
                handleRouteChange(route, isBottomBarVisible)
            },
            controllerFactory: { tabBar, routeHandler in
                MainViewControllerKt.makeFoldersViewController(
                    tabBarVisibility: nil,
                    onRouteChanged: routeHandler
                )
            }
        )
        .id(themeHostIdentifier)
        .ignoresSafeArea(edges: .vertical)
        .tabItem { Label("Folders", systemImage: "folder") }
        .tag(Tab.folders)

        ComposeHost(
            tabBar: tabBar,
            onRouteChanged: { route, isBottomBarVisible in
                handleRouteChange(route, isBottomBarVisible)
            },
            controllerFactory: { tabBar, routeHandler in
                MainViewControllerKt.makeSettingsViewController(
                    tabBarVisibility: nil,
                    onRouteChanged: routeHandler
                )
            }
        )
        .id(themeHostIdentifier)
        .ignoresSafeArea(edges: .vertical)
        .tabItem { Label("Settings", systemImage: "gearshape") }
        .tag(Tab.settings)
    }
    .preferredColorScheme(darkThemeEnabled ? .dark : .light)
    .onChange(of: darkThemeEnabled) { _ in
        // Keep the user on Settings after theme-triggered controller rebuilds.
        selection = .settings
    }
    .toolbar(tabBar.isVisible ? .visible : .hidden, for: .tabBar)
    .animation(.easeInOut, value: tabBar.isVisible)
}

A few key points:

  • Each tab is a ComposeHost that embeds one Kotlin UIViewController.
  • controllerFactory is a closure that knows how to ask Kotlin for the right controller (Notes, Folders, Settings). Notice that tabBarVisibility is passed as nil now so there is only one source of truth for visibility: the route callback.
  • onRouteChanged is wired to handleRouteChange to keep selection and tabBar.isVisible in sync with Kotlin.
  • .toolbar(tabBar.isVisible ? .visible : .hidden, for: .tabBar) integrates with the system tab bar APIs on modern iOS, so the OS can animate the Liquid Glass bar in and out.

On recent iOS versions, a TabView is rendered with the floating glass style. That means you do not implement Liquid Glass yourself. You simply tell the system when the tab bar should be visible and which tab is selected. The OS applies the effect.

themeHostIdentifier is used with .id(...) to force a rebuild of the Compose host when the theme changes so that Compose can pick up the new dark or light mode.

5. ComposeHost: from Kotlin controllers to SwiftUI

ComposeHost is a small UIViewControllerRepresentable wrapper that takes a factory closure to create the Kotlin controller and a callback to send route changes back to LiquidRoot:

private struct ComposeHost: UIViewControllerRepresentable {
    @ObservedObject var tabBar: TabBarVisibility
    let onRouteChanged: (String, Bool) -> Void
    let controllerFactory: (TabBarVisibility, @escaping (String, KotlinBoolean) -> Void) -> UIViewController

    func makeCoordinator() -> Coordinator {
        Coordinator(onRouteChanged: onRouteChanged)
    }
    func makeUIViewController(context: Context) -> UIViewController {
        context.coordinator.onRouteChanged = onRouteChanged
        let controller = controllerFactory(tabBar, context.coordinator.routeHandler)
        applyTabBarVisibility(for: controller, coordinator: context.coordinator, visible: tabBar.isVisible)
        return controller
    }
    func updateUIViewController(_ uiViewController: UIViewController, context: Context) {
        context.coordinator.onRouteChanged = onRouteChanged
        applyTabBarVisibility(for: uiViewController, coordinator: context.coordinator, visible: tabBar.isVisible)
    }
}

The nested Coordinator caches the last route and visibility to skip duplicate updates and exposes a routeHandler closure in the signature Kotlin expects:

final class Coordinator {
    var onRouteChanged: (String, Bool) -> Void
    var cachedTabBarHeight: CGFloat?
    private var lastRoute: String?
    private var lastVisible: Bool?

    init(onRouteChanged: @escaping (String, Bool) -> Void) {
        self.onRouteChanged = onRouteChanged
    }
    lazy var routeHandler: (String, KotlinBoolean) -> Void = { [weak self] route, isBottomBarVisible in
        guard let self else { return }
        let visible = isBottomBarVisible.boolValue
        if route == lastRoute && visible == lastVisible {
            return
        }
        lastRoute = route
        lastVisible = visible
        self.onRouteChanged(route, visible)
    }
}

Kotlin calls this routeHandler whenever onRouteChanged is invoked in the shared UI.

ComposeHost also calls applyTabBarVisibility so that changes in TabBarVisibility are reflected in the underlying UIKit controller, not just in SwiftUI.

6. Handling tab bar visibility, including pre-modern iOS

applyTabBarVisibility is responsible for mapping tabBar.isVisible to the real UITabBarController:

private func applyTabBarVisibility(for controller: UIViewController, coordinator: Coordinator, visible: Bool) {
    guard let tabController = findTabBarController(startingFrom: controller) else { return }
    let targetHidden = !visible

    if #available(iOS 18.0, *) {
        guard tabController.tabBar.isHidden != targetHidden else { return }
        tabController.setTabBarHidden(targetHidden, animated: true)
        return
    }
    if tabController.tabBar.isHidden == targetHidden && tabController.tabBar.alpha == (visible ? 1 : 0) {
        return
    }
    if coordinator.cachedTabBarHeight == nil {
        let height = tabController.tabBar.bounds.height
        if height > 0 {
            coordinator.cachedTabBarHeight = height
        }
    }
    let measuredHeight = coordinator.cachedTabBarHeight ?? tabController.tabBar.bounds.height
    let baseHeight = measuredHeight > 0 ? measuredHeight : 49
    let additionalInset = targetHidden ? -baseHeight : 0
    if tabController.additionalSafeAreaInsets.bottom != additionalInset {
        tabController.additionalSafeAreaInsets.bottom = additionalInset
        var frame = tabController.view.frame
        frame.size.height += 0.1
        tabController.view.frame = frame
        frame.size.height -= 0.1
        tabController.view.frame = frame
        tabController.view.setNeedsLayout()
        tabController.view.layoutIfNeeded()
    }
    if targetHidden {
        UIView.animate(withDuration: 0.2) {
            tabController.tabBar.alpha = 0
        } completion: { _ in
            tabController.tabBar.isHidden = true
        }
    } else {
        tabController.tabBar.isHidden = false
        tabController.tabBar.alpha = 0
        UIView.animate(withDuration: 0.25) {
            tabController.tabBar.alpha = 1
        }
    }
}

This function:

  • Walks up the parent chain to find the nearest UITabBarController.
  • On iOS 18 and newer, uses the new setTabBarHidden(_:animated:) API. That is where you get the correct system animation and behavior for the Liquid Glass tab bar.
  • On older releases, adjusts additionalSafeAreaInsets.bottom and alpha, with a small frame jiggle to force layout.

The result is:

  • You can fully control whether the Liquid Glass tab bar is visible, even when embedding your own UIViewController tree from Kotlin.
  • You get correct safe area behavior when the bar hides and shows.

7. Handling route changes in LiquidRoot

The core routing bridge lives in handleRouteChange:

private func handleRouteChange(_ route: String, _ isBottomBarVisible: Bool) {
    let resolved = Tab(routeID: route)
    let shouldShow = resolved != nil && isBottomBarVisible
    NSLog(
        "RouteChange route=%@ bottomBar=%d resolved=%@ currentVisible=%d shouldShow=%d",
        route,
        isBottomBarVisible ? 1 : 0,
        String(describing: resolved),
        tabBar.isVisible ? 1 : 0,
        shouldShow ? 1 : 0
    )
    if route == lastRouteHandled && shouldShow == lastShouldShow {
        return
    }
    lastRouteHandled = route
    lastShouldShow = shouldShow
    if route == Self.lastRouteHandledGlobal && shouldShow == Self.lastShouldShowGlobal {
        return
    }
    Self.lastRouteHandledGlobal = route
    Self.lastShouldShowGlobal = shouldShow
    if (tabBar.isVisible != shouldShow) {
        Self.updateOnMain {
            tabBar.isVisible = shouldShow
        }
    }
    if let resolved, selection != resolved {
        selection = resolved
    }
}

What this does step by step:

  1. Maps the route string coming from Kotlin into a Tab value using the enum initializer. If the route cannot be mapped, there is no tab to select.
  2. Computes shouldShow:
    - The bottom bar should be visible only if the route maps to a tab, and Kotlin asked for the bar to be shown (isBottomBarVisible).
    - Detail screens like note/123 may hide the bar even though they belong to the Notes tab.
  3. Uses both instance and global caches (lastRouteHandled, lastRouteHandledGlobal, etc.) to skip redundant work when the same route and visibility are emitted multiple times.
  4. If tabBar.isVisible does not match shouldShow, updates it, which in turn:
    - Updates the SwiftUI toolbar visibility.
    - Triggers applyTabBarVisibility through ComposeHost.
  5. If resolved is non nil and does not match the current selection, updates selection so the correct tab is highlighted.

This is the heart of the KMP plus Liquid Glass integration:

  • Kotlin decides what route you are on and whether the bar should show.
  • LiquidRoot simply translates that into tab selection and tab bar visibility for the native Liquid Glass tab bar.

8. Hooking LiquidRoot into the iOS lifecycle

The rest of the file is plumbing, but it is worth seeing the connections.

The SceneDelegate uses LiquidRoot in a UIHostingController:

final class SceneDelegate: UIResponder, UIWindowSceneDelegate {
    var window: UIWindow?

    func scene(
        _ scene: UIScene,
        willConnectTo sessimion: UISceneSession,
        options connectionOptions: UIScene.ConnectionOptions
    ) {
        guard let windowScene = scene as? UIWindowScene else { return }
        let bg = UIColor.systemBackground
        let host = UIHostingController(rootView: LiquidRoot())
        host.view.isOpaque = true
        host.view.backgroundColor = UIColor(named: "AppBackground")
        let window = UIWindow(windowScene: windowScene)
        window.isOpaque = true
        window.backgroundColor = bg
        window.rootViewController = host
        self.window = window
        window.makeKeyAndVisible()
    }
}

The SwiftUI @main entrypoint also uses LiquidRoot:

@main
struct AmazingNoteiOSApp: App {
    @UIApplicationDelegateAdaptor(AppDelegate.self) private var appDelegate

    var body: some Scene {
        WindowGroup {
            LiquidRoot()
                .onOpenURL { url in
                    _ = GIDSignIn.sharedInstance.handle(url)
                }
        }
    }
}

AppDelegate sets up Firebase and Crashlytics, and provides a UISceneConfiguration that points to SceneDelegate, so both the SwiftUI and UIKit style entrypoints end up hosting the same LiquidRoot view.

That means:

  • There is exactly one place, LiquidRoot, where you define iOS tabs.
  • Every path into the app runs through the Liquid Glass tab shell.

9. Android side: reusing the same route model

On Android, you do not have Liquid Glass, but you can reuse exactly the same route model from Kotlin to drive a bottom navigation bar in Compose.

A typical shared Composable might look like:

@Composable
fun AmazingNoteAppAndroid() {
    val navState = rememberAppNavigationState() // exposes currentRoute and navigate()

    Scaffold(
        bottomBar = {
            if (navState.currentRoute.shouldShowBottomBar()) {
                NavigationBar {
                    NavigationBarItem(
                        selected = navState.currentRoute.isNotes(),
                        onClick = { navState.navigateToNotesRoot() },
                        icon = { Icon(Icons.Default.Note, contentDescription = "Notes") },
                        label = { Text("Notes") }
                    )
                    NavigationBarItem(
                        selected = navState.currentRoute.isFolders(),
                        onClick = { navState.navigateToFoldersRoot() },
                        icon = { Icon(Icons.Default.Folder, contentDescription = "Folders") },
                        label = { Text("Folders") }
                    )
                    NavigationBarItem(
                        selected = navState.currentRoute.isSettings(),
                        onClick = { navState.navigateToSettingsRoot() },
                        icon = { Icon(Icons.Default.Settings, contentDescription = "Settings") },
                        label = { Text("Settings") }
                    )
                }
            }
        }
    ) { padding ->
        Box(Modifier.padding(padding)) {
            ScreenHost(navState.currentRoute)
        }
    }
}

Notice the symmetry:

  • On Android, you read currentRoute directly to decide if the bar should be visible and which item should be selected.
  • On iOS, you receive routeId and isBottomBarVisible through the callback and use Tab plus TabBarVisibility to drive the native Liquid Glass tab bar.

Both platforms share the same core navigation concepts. The difference is only in the shell.

10. Takeaways and pattern recap

The Amazing Note codebase shows a neat way to combine:

  • Shared UI and navigation logic in Kotlin using Compose
  • Native Liquid Glass tab bar on modern iOS
  • A Material bottom navigation bar on Android

The pattern is:

  1. Model navigation in shared code
    Give every screen a route ID and a boolean that says whether the bottom bar should be visible.
  2. Emit route changes to the host platform
    Provide an onRouteChanged(routeId: String, bottomBarVisible: Boolean) callback in your Kotlin entrypoint and call it from your root Composables.
  3. On iOS, wrap Compose in a SwiftUI TabView
    Use LiquidRoot.swift style code:
    - Create one ComposeHost per tab, each backed by a Kotlin controller.
    - Feed route changes into a small Tab enum and TabBarVisibility observable.
    - Use .toolbar(..., for: .tabBar) and setTabBarHidden to show or hide the system Liquid Glass tab bar.
  4. On Android, draw a regular bottom nav in Compose
    Use the same route model to decide what to show and when.
  5. Keep visual responsibility on the host, navigation responsibility in shared code
    Kotlin never tries to draw the Liquid Glass tab bar. It just describes which tab you are on and whether the bar should exist. SwiftUI and UIKit take care of the rest.

If you want to extend this pattern further, you can add more root tabs, have per-tab back stacks in shared code, or even expose more nuanced visibility states (for example, a compact bar on detail screens) while still letting the OS handle Liquid Glass and animation on iOS.
